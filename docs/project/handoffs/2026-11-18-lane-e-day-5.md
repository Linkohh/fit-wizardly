## Change of approach (the brief said otherwise)
The brief said to add `updatedAt` to every stored item type and call `markDirty` from every store action. Instead, a **tracker** watches each store. The stores are immutable, so it compares records before and after each change and marks the changed keys dirty, or deleted.
- **Why:**
  - It catches every action, including ones added later, so a forgotten `markDirty` can't silently lose sync.
  - It needs no change to the stored data shapes or to the ~30 store actions.
  - The outbox entry already holds the edit time. A record without one has been synced already, so "cloud wins" is the right rule for it.
- **Traps handled, each with a test:**
  - Loading the saved copy at startup isn't counted as an edit: tracking starts after hydration.
  - Records written from a pull aren't pushed back.
  - Unrelated store changes, such as the current week or the selected date, don't mark anything.
- `CONTRACTS.md` #5 is updated.

## How it was verified
- **Round trip:** every collection's `toRow` → JSON (as the server returns it) → `fromRow` gives back the same record and key.
- **Tracking:** add, edit and delete each mark the right key, and a delete is marked as a delete.
- **Two devices through the fake database:**
  1. Phone A logs a measurement, a meal, a check-in, a workout and a streak, then syncs.
  2. A fresh phone B on the same account pulls them all. Dates come back as `Date` objects, and nothing is queued to be sent back.
  3. B deletes the measurement and the cloud gets a tombstone.
- **First sign-in:** a record saved before tracking existed isn't in the outbox. After `markAllCollectionsDirty()`, it uploads.
- **Checked that the tests catch real bugs.** I broke the tracker three ways: pulled records pushed back, tracking started before the saved copy loaded, and deletions not marked. Each made a test fail. The file was restored and compared byte for byte.
