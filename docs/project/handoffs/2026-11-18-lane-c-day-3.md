## What changed
- **`src/lib/monitoring.ts` (new, contract #8):** `initMonitoring()` and `captureError()`, exactly as published.
  - `initMonitoring()` returns straight away when `VITE_SENTRY_DSN` is empty. It registers no listener and loads nothing. With a DSN, it starts Sentry only if `hasAnalyticsConsent()` is true. It also listens for `CONSENT_RESOLVED_EVENT`, so Sentry starts as soon as the user opts in. It initialises once.
  - The SDK is loaded with a dynamic import, never statically.
  - **With no DSN at build time, Vite inlines the empty value and drops the import as dead code.** The current production build contains no Sentry code at all (checked: `grep` for Sentry symbols in `dist/` finds 0 files).
  - Init options: `release: __APP_VERSION__`, `environment: import.meta.env.MODE`, `tracesSampleRate: 0` (errors only).
  - **`sendDefaultPii` does not exist in Sentry SDK v11.** It was replaced by `dataCollection`. I set its strictest values (`NO_PII_DATA_COLLECTION`): user info, cookies, headers, query params and local variables off; no HTTP bodies.
  - `beforeSend` (`scrubEvent`): strips the query string and hash from `request.url`, drops `request.query_string` and `cookies`, removes `extra` keys that look like health data (weights, measurements, body fat, food, meals, macros, calories, sleep, heart rate, injuries), and strips query strings from breadcrumb URLs.
  - `beforeBreadcrumb` (`scrubBreadcrumb`): drops console breadcrumbs, because console output can echo app state such as weights or meals.
  - `captureError(error, context?)` forwards to Sentry once it is running, otherwise it calls `console.error`. It never throws.
- **Package:** `@sentry/react` was added as asked. The code imports `@sentry/browser` (the same SDK and version, 11.14.0, added as an explicit dependency). The reason is under "For other lanes": importing from `@sentry/react` would put the whole SDK into the preloaded `vendor-react` chunk once a DSN is set. `@sentry/capacitor` is not added; native setup is a Lane H follow-up after Gate 2.
- **`src/main.tsx`:** calls `initMonitoring()` before render.
- **`src/components/ErrorBoundary.tsx`:**

  - New optional `renderFallback({ error, reset })` prop, so a fallback can reset the boundary.

## For other lanes
- **To Lane D (`vite.config.ts`, `build.rollupOptions.output.manualChunks`). This must land before L6 sets a DSN.** With a DSN set at build time, two existing rules pull Sentry into chunks that are preloaded at startup:
  - `id.includes("/react/")` matches `node_modules/@sentry/react/`. With a namespace import, this grew `vendor-react` from 257 KB to 700 KB. I avoided it by importing `@sentry/browser`.
  - `id.includes("zod")` matches `node_modules/@sentry/core/build/esm/integrations/zoderrors.js`. Rollup then pulls shared Sentry core code into `vendor-data`: about **20 KB** (149,554 vs 129,751 bytes) that is preloaded. I can't fix this from my files.

  The fix is one line at the top of the `if (id.includes("node_modules"))` branch:

  ```ts
  if (id.includes("/node_modules/@sentry/")) return "vendor-sentry";
  ```

  Also add `!dep.includes("vendor-sentry") &&` to the `modulePreload.resolveDependencies` filter. After that, `monitoring.ts` can import `@sentry/react` again (a one-word change) and `@sentry/browser` can be dropped. Check: `VITE_SENTRY_DSN=https://public@o1.ingest.de.sentry.io/1 npx vite build`. `vendor-react` and `vendor-data` should come out the same size as a build without the DSN.
- **To Lane H:** add `@sentry/capacitor` after Gate 2 if native crash reports are wanted. `initMonitoring()` is the single place to wire it in.
- **To everyone:** `captureError(error, { key: 'value' })` from `@/lib/monitoring` is safe to call anywhere. Don't put health values in `context`: keys that look like health data are dropped, but values under other keys are not inspected.
