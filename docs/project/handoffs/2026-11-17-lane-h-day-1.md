## What removing CapacitorHttp changes
- **Before:** on native, Capacitor replaced `window.fetch`/XHR with its native HTTP client. Requests skipped CORS and the WebView's network stack.
- **Now:** native requests go through the WebView exactly as on the web (origin `capacitor://localhost` on iOS, `https://localhost` on Android). Cross-origin hosts must send CORS headers.
- **Affected call sites:**
  - `src/features/exercise-library/service.ts:267` (`fetchWithTimeout`): calls `https://wger.de/api/v2/exerciseinfo/` **directly on native** and uses `/api/proxy-wger` on the web.
  - `src/lib/services/api/exerciseApiAdapter.ts:26` (`WgerAdapter.search`): calls wger directly on **both** web and native. Because this already runs in browsers, and `vercel.json`'s CSP allows `connect-src https://wger.de`, wger is expected to send `Access-Control-Allow-Origin` for `/api/` (wger's Django settings use django-cors-headers for the API, as far as I know). **I couldn't confirm it**: this environment's network policy blocks `wger.de` (proxy 403).
  - Not affected: Supabase (sends CORS) and Open Food Facts (already called directly from the web, so it already needs CORS).
  - Relative `/api/*` calls (`motivationQuoteClient.ts`, `exerciseApiAdapter.ts:95`) never worked on native, with or without CapacitorHttp, because they resolve to `capacitor://localhost/api/...`. Day 2's `apiUrl()` fixes that.
- **Plan for Day 2:** change the native branch at `service.ts:267` to `apiUrl('/api/proxy-wger?url=…')`, so native uses the same proxy as the web and no longer depends on wger's CORS. Do the same for `WgerAdapter.search` if wger's CORS turns out to be missing. If the snapshot sync fails on native in the meantime, the app keeps the bundled snapshot (`source: 'snapshot'`), so the library still works, only possibly stale.
