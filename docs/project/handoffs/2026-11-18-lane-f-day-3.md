## What changed
- **`supabase/functions/delete-account/`** (new, contract #4):
  - `handler.ts`: all the logic, with no imports, so it can be tested with a mocked client.
    - `OPTIONS` → 204. Other methods → 405. Missing or non-Bearer token → 401.
    - Verifies the token with `createClient(url, anonKey, { global: { headers: { Authorization } } }).auth.getUser(token)`. A GoTrue 4xx gives 401; a 5xx or network error gives 500 (not a misleading 401).
    - Calls `auth.admin.deleteUser(<id from the verified token>)` with `SUPABASE_SERVICE_ROLE_KEY` → 204.
    - Any failure → `500 {"error":"Deletion failed"}`, with details logged server-side only.
    - CORS: echoes the origin only if it's `capacitor://localhost`, `https://localhost`, or listed in the `ALLOWED_ORIGINS` secret (comma-separated, trailing `/` ignored). `Vary: Origin` is set.
  - `index.ts`: `Deno.serve(createHandler({ createClient, getEnv: Deno.env.get }))`.
  - `index.test.ts`: 15 Deno tests covering 401 (no header, bad scheme, invalid token, no user), 204 (and that it uses the anon key plus the caller header for `getUser` and the service key with no caller header for the delete, and deletes exactly the verified id), 500 (admin failure, GoTrue 5xx, thrown error, missing secret; no detail leaks), 405, preflight, disallowed origin, CORS on every status, and the parsers.
  - `README.md`: deploy commands for Lincoln (`supabase secrets set ALLOWED_ORIGINS=…`, `supabase functions deploy delete-account`), a note on `verify_jwt`, a curl test (401, preflight, 204, then 401 again), and a SQL check for leftovers.
- **`supabase/tests/delete_account.test.sql`** (new): the cascade check on top of 008.
  - **Coverage:** user A gets a row in every public column that references `auth.users` or `profiles` (22 today). The test fails if a future table isn't seeded.
  - `authenticated` can't delete from `auth.users`.
  - The delete works as a role with **no grants in `public`** (as GoTrue's role does): cascades don't depend on the deleter and RLS doesn't block them.
  - Afterwards nothing points at A. A's circle and challenge survive with `created_by = NULL`; B's challenge loses `winner_id`. B's footprint is unchanged, apart from B's reaction on A's deleted activity, and B can still read their rows under RLS.
- **`docs/SECURITY.md`:** rewritten from scratch to match the code. It covers:
  - the auth model (email OTP plus the 6-digit code, the sessionStorage session, `RequireAuth` as UX only, trainer-role lock)
  - an RLS table per table, checked against `pg_policies` from the harness
  - rules for new tables
  - **the service-role key exists only as a secret in this one function**
