## What changed
- **`supabase/migrations/009_purge_tombstone_content.sql` (DEBT-097, Lincoln's decision: wipe).** One trigger function, `public.purge_tombstone_content()`, attached `BEFORE INSERT OR UPDATE` to `plans` and the seven 007 tables. When `NEW.deleted_at IS NOT NULL` it replaces every content column with an empty or neutral value that passes the table's constraints. Live rows aren't touched, so a revive (upsert with full content, `deleted_at` NULL) works. An unknown table raises an error rather than silently keeping content. Re-runnable (`CREATE OR REPLACE`, `DROP TRIGGER IF EXISTS`); 007 and 008 are not edited.

Why the kept columns stay:
- **`user_id`:** RLS, the account-deletion cascade and the primary key need it.
- **`id` / `day`:** the pull needs the key to delete the right local record, and the revive upsert's `ON CONFLICT` needs it to find the row.
- **`deleted_at`:** it is the tombstone, and it's compared with pending local edits.
- **`updated_at`:** the pull cursor; without it moving, other devices never see the delete.
- **`plans.created_at`:** a judgement call, flagged below.

### Tests (all eight tables)
1. A live row keeps its content.
2. `UPDATE ... SET deleted_at`: content is wiped; the key, `user_id` and `deleted_at` survive; `updated_at` moves.
3. A revive with full content restores the row.
4. An upsert carrying `deleted_at` over an existing row (update path) wipes it.
5. An upsert carrying `deleted_at` for a new key (insert path) wipes it. The one-row-per-user tables only have the update path.
6. A second revive works.
7. User B can't read, tombstone, revive or upsert onto A's row, and A's row is unchanged afterwards.
8. A catalog guard: every column of each table must be either kept or cleared, and each table has exactly one purge trigger. A new content column fails the test until 009 covers it.
