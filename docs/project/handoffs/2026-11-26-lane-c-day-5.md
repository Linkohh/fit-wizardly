## What changed
- **Two separate toggles, both off by default** (`src/components/legal/ConsentModal.tsx`):
  - **"Send crash reports"** (Sentry), stored as `CRASH_REPORTS_CONSENT_STORAGE_KEY` = `fitwizard_crash_reports_consent`.
  - **"Share anonymous usage statistics"** (PostHog and Vercel Web Analytics), stored as the existing `ANALYTICS_CONSENT_STORAGE_KEY` = `fitwizard_analytics_consent`. This replaces "Help improve FitWizard".
  - Each toggle has a one-line description saying what is sent and to whom. A shared line says that neither one sends workouts, weights, body measurements or meals. Both new text blocks go through `t()`, and the keys (`consent.diagnostics_*`, `consent.crash_reports_*`, `consent.analytics_*`, `consent.change_later`) are in `en`, `es`, `de` and `pt`. The `localeGaps.json` ratchet doesn't grow.
  - When the tray is reopened from **Profile → Details → Privacy Settings** (`requestConsentModal`, already wired), it shows each stored choice. Profile wasn't touched.
- **Revoking works without a reload**, triggered by `CONSENT_RESOLVED_EVENT` or by a `storage` event from another tab:
  - **Sentry** (`src/lib/monitoring.ts`) now reads only the crash-reports key. Turning it off calls `Sentry.close()` and turns `captureError` back into `console.error`. Turning it back on starts a new client. `beforeSend` also drops any event when consent is missing, and a load already in progress won't init after a revoke.
  - **PostHog** (`src/lib/analytics/track.ts`, new `syncAnalyticsConsent()`): turning it off calls `posthog.opt_out_capturing()`. The new config option `opt_out_persistence_by_default: true` makes that opt-out also **delete PostHog's stored anonymous id**. Turning it back on calls `opt_in_capturing({ captureEventName: false })`, so no `$opt_in` event is sent. On a later page load, our consent key overrides any opt-out flag PostHog left in storage.
  - **Vercel Analytics** unmounts as before through `useAnalyticsConsent()` in `App.tsx`. There is now a test for this.
- **`src/lib/consent.ts`:** adds `hasCrashReportsConsent()` and `onConsentChange(listener)`, which covers the modal event plus other tabs' `fitwizard_*` storage changes. If storage is blocked (private mode), every flag reads as "no" instead of throwing.
- **DEBT-061, write side:** `ConsentModal` no longer calls `analyticsStore.setConsent`, so nothing writes the `fitwizard-analytics.hasConsented` copy any more. The store itself still has the field (see "For other lanes").
- **Tests:** `ConsentModal.test.tsx` covers both toggles off by default, each one stored on its own, revoking one without touching the other, keys written before the event, an existing analytics opt-in kept, and no write to the legacy key. `monitoring.test.ts` and `monitoring.consent.test.tsx` cover the analytics opt-in not starting Sentry, `Sentry.close()` on revoke (same tab, another tab, and through the real modal), restarting after re-consent, and a revoke during load. `track.test.ts` covers `opt_out_capturing()` on revoke (same tab and another tab), opting back in with no `$opt_in` event, and clearing a stale opt-out left in storage. `App.auth-routing.test.tsx` covers Vercel Analytics unmounting on revoke. The new `consent.test.ts` covers separate keys, blocked storage and `onConsentChange`.

## Decisions
- **Existing users:** anyone who already has `fitwizard_analytics_consent = 'true'` keeps analytics on. Their key and its meaning are unchanged.
- **Crash reports start off for everyone, existing users included.** Reason: until today, opting in meant agreeing to "anonymous usage data". Nobody was asked about crash reports on their own, and Sentry hasn't been live yet (no DSN before L6). So reading the old analytics "yes" as a crash-reports "yes" would mean consent the user never gave, which the separate-consent rule exists to stop. The cost is that existing users won't send crash reports unless they open Privacy Settings, because the tray doesn't reopen for anyone who already agreed. See question 2.

### `Legal.tsx`: disclosure blocks (replace the Day 3 and Day 4 drafts)

> **Crash reports (Sentry)**
> - **Tool:** Sentry, from Functional Software, Inc.
> - **Purpose:** to find and fix errors that break the app.
> - **What is sent:** only when the app hits an error: the error message and stack trace, the part of the screen where it happened, the app version, your browser and operating system, and the page path without query strings. Crash reports never include your name, email, account ID, cookies, or any workout, body, readiness or nutrition data. Sentry sees your IP address when a report arrives, but our project is set not to store it.
> - **Where:** Sentry's [EU (Frankfurt) / US] data region. *(Lincoln confirms at L6; EU recommended.)*
> - **How long:** Sentry's default retention for our plan, [90 days]. *(Lincoln confirms.)*
> - **Your choice:** off unless you turn on "Send crash reports". Turn it off at any time in Profile → Details → Privacy Settings. Reporting stops straight away, with no reload.

> **Usage statistics (PostHog)**
> - **Tool:** PostHog, from PostHog Inc.
> - **Purpose:** to learn which features people use, so we know what to improve.
> - **What is sent:** anonymous events: which screens you open, and when you finish steps such as creating a plan, starting or finishing a workout, logging a meal or signing in. Events can include a few general details: your goal type, days per week, number of exercises, workout length in minutes, and whether you use the web, iOS or Android app. Events never include your name, email, account ID, weights, reps, body measurements, readiness answers or what you eat. Page addresses are sent without query strings, and IDs and invite codes in them are removed. PostHog keeps a random identifier in your browser's local storage to group events from one device. That identifier is deleted when you turn usage statistics off. Session recording, automatic click tracking and surveys are off. PostHog sees your IP address when an event arrives, but our project is set not to store it. *(Lincoln confirms the PostHog project setting "Discard client IP data" at L6.)*
> - **Where:** PostHog EU Cloud (Frankfurt, Germany).
> - **How long:** PostHog's default retention for our plan. *(Lincoln confirms.)*
> - **Your choice:** off unless you turn on "Share anonymous usage statistics". Turn it off at any time in Profile → Details → Privacy Settings. Sending stops straight away, with no reload.

> **Usage statistics (Vercel Web Analytics)**, website only, covered by the same "Share anonymous usage statistics" switch
> - **Tool:** Vercel Web Analytics, from Vercel Inc.
> - **Purpose:** to count page visits and see which pages are used.
> - **What is sent:** the page address and the page you came from, plus your browser, operating system, device type and the country worked out from your IP address. Vercel Web Analytics sets no cookies. It doesn't store your IP address. To count unique visits, it uses a short-lived hash that is discarded within a day. It isn't used in the iOS or Android apps. *(Lincoln checks this paragraph against Vercel's Web Analytics privacy page.)*
> - **Where:** Vercel's infrastructure. *(Lincoln confirms the region in the Vercel dashboard; Vercel is US-based.)*
> - **How long:** Vercel's default retention for Web Analytics on our plan. *(Lincoln confirms.)*
> - **Your choice:** the same switch as PostHog. Turning it off stops Vercel Web Analytics straight away, with no reload.
